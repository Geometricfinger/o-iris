# Hardware-ready program: what is built, what the parts will tune, how to check it

The owner's request (2026-11-17), verbatim:

> After your done everything in oris build out that was speculative we can write the code and reasoning without the parts and pieces to prepare atleast the codebase and infrastructure to later be fine tuned

This document maps that build-out. What has been seen working on real hardware, and what the automated checks prove, is summarised in [EVIDENCE.md](EVIDENCE.md). For every part that depends on hardware this document says:
- what is built and tested now;
- which named constants or placeholders the real parts will tune, and where they are;
- what to measure on the device, with the pass condition when an ADR or the build spec gives one.

**Target platforms** ([ADR-0059](adr/0059-code-first-build-order.md) decision 1): open-platform Android smart glasses first, then possibly a helmet with smart glasses, more sensors and cameras. The Mac and the Pi rig stay as test benches. No glasses have been chosen or bought.

**The rule** (ADR-0059 decision 2): code built for glasses is "built", not "working on glasses", until it has run on them. Everything below runs in tests, in simulation, on loopback links or in JVM checks. None of it has run on glasses, a helmet, a phone or a Pi. docs/STATUS.md keeps "built" apart from "observed on hardware", and the spec's gates still govern every claim about device performance.

Status words used in the table:
- **Built, simulated:** code and tests exist; inputs are synthetic or simulated.
- **Wired:** `oiris run` (live mode) uses it when configured.
- **JVM-checked:** the Kotlin twin in `android/core` matches Python on shared vectors (`tests/vectors/*.json`), run by `gradle :core:check` on the development Mac.
- **Not on hardware:** never run on the target device.

## Owner decisions still open
