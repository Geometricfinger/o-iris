### Added (live camera and clip privacy; ADR-0057 decision 5)

### Added (live mode and the macOS app; ADR-0056)
- Live mode `oiris run` (`oiris/live.py`, docs/LIVE.md), now the default command: plain `oiris` runs it. It asks for the passphrase or uses `OIRIS_PASSPHRASE`, creates or unlocks the encrypted store, resolves adapters by name (unavailable ones reported, not fatal), steps the Engine in a background thread at `live.hz` (default 1, at most 10), records one sweep per session (`done` on Quit or `--duration`, `interrupted` on SIGTERM/SIGINT) and serves the dashboard on 127.0.0.1. Tests: `tests/test_live.py`.
- Live storage: the retention purge (config `retention_days`, default 30) runs when the store opens and every 24 h. A sighting is written when the (signature, level) pair changes, else at most once per 60 s; the sweep counts and the snapshot's `records` show `events`, `sightings`, `sightings_suppressed` and `purged_rows`.
- Live network guard: non-loopback `connect`, `connect_ex`, `sendto` and `sendmsg` on Python sockets are refused while live mode runs. It does not police subprocesses or native code.
- macOS sensors: `ble_scan` on CoreBluetooth with a Bluetooth permission gate (`BlePermission`; waits while undecided, fails with a plain reason if denied), and `wifi_macos` (`oiris/adapters/macos.py`), which reads only the O Iris.app launcher's Wi-Fi feed and shows "waiting for Location permission" until Location is allowed. `pip install -e ".[mac]"` installs bleak and its pyobjc packages. Tests: `tests/test_macos_adapters.py`.
- O Iris.app: compiled Swift launcher (`macos/launcher/`) that asks for Bluetooth and Location (When In Use, only to unlock Wi-Fi network IDs; never reads a position) and runs oiris as its child; Wi-Fi feed from `CWInterface.cachedScanResults()` every 15 s over a pipe (no scan of its own); macOS passphrase dialog; offline install from bundled wheels for Python 3.11–3.14; the M-15 `keychain-gate` compiled into the bundle; ad-hoc signature verified with `codesign --verify --deep --strict`. Apple Silicon with macOS 14 or later only. Tests: `tests/test_macos_app.py`.
- Dashboard as an app screen: "No live data yet" until a signal family is active, plain sensor status with what to do (D5), a Quit button (POST with a per-run token and same Origin; recorded as `done`), and a Host check on every GET (127.0.0.1/localhost on the dashboard port, else 403).
- Engine: each adapter's readings are judged by that adapter's own maximum age (`AdapterBase.max_age_s`, at least `sensor_max_age_s`), so slow Wi-Fi feed readings stay current between lines.
- Bus: when a read returns nothing, the adapter's own health and reason are shown (for example "waiting for Bluetooth permission"); a `health()` that raises is logged once per change.

### Fixed (M-16 on a real Mac webcam; found in a live check on 2026-11-15)
- `oiris face-match fetch-models` failed with CERTIFICATE_VERIFY_FAILED on python.org's macOS Python (no root certificates until "Install Certificates.command" runs). The download now verifies against certifi's CA bundle, else pip's vendored copy, else the default (a user-set `SSL_CERT_FILE` wins); if verification still fails, `ModelMissing` says how to fix it. Checksums stay mandatory.
- Five-angle enrollment could not complete on a laptop webcam: deliberate head tilts never reached the fixed up/down pose thresholds. UP/DOWN are now judged against the person's own accepted FRONT pitch (`face_match.pose_up_delta` 0.06, `pose_down_delta` 0.08, provisional); without a pitch the old rule applies. The five required angles and matching are unchanged.
- `oiris face-match enroll --camera 0` silently used an iPhone (Continuity Camera): OpenCV's camera numbering can differ from macOS's list. New `--camera auto` uses the first camera that sees one face; captures drop a just-opened camera's dark first frames.
- The strictest jurisdiction requires a consent record, but nothing could create one, and enroll crashed with ConsentError. New `oiris face-match consent --subject CODE [--days N]` records the user's own consent after a typed YES (`--withdraw --id ID` withdraws it and erases templates enrolled under it); enroll now prints the reason and continues.
- Live check after the fixes (one consenting user, a Mac's built-in camera): camera auto-pick chose the Mac's camera; five-angle enrollment completed; 20/20 frames matched at confidence 0.929-0.943 (threshold 0.8); camera covered, 0/20 faces. Not a study; tests stay synthetic.
### Fixed (F3 follow-up: durable consent)
- `ConsentRegistry(db)` persists grants, withdrawals and expiry in the encrypted store (migration v5 `consent_record`, body sealed with the DB key, AAD bound to the consent ID); withdrawal is written before hooks run. M-16 uses the durable registry by default and, on load, crypto-erases (verified, `consent_withdrawn` logged) templates whose consent is withdrawn or expired. - F3 M-16: consent is rechecked on every template load/match and on `ConsentRegistry.withdraw`; templates under a withdrawn or expired consent are purged through the same verified crypto-erase as person deletion (`consent_withdrawn` change-log entry).
