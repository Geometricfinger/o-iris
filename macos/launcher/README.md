# App launcher
Swift CLI (Foundation, CoreBluetooth, CoreLocation, CoreWLAN) compiled as `O Iris.app/Contents/MacOS/o-iris`, the bundle's `CFBundleExecutable`. It does three things:

1. **Asks for the permissions itself**, at launch and before anything else: it creates a `CBCentralManager` (main queue, no power alert), which makes macOS show the Bluetooth prompt for O Iris while the authorization is undecided, and a `CLLocationManager` that calls `requestWhenInUseAuthorization()` while the Location authorization is `notDetermined`. It never scans, connects, starts location updates or reads a position. It appends each Bluetooth state/authorization change and each Location authorization change to `~/Library/Logs/O Iris/o-iris.log` (`o-iris: ...` lines).
2. **Stays the responsible process**: it runs `Contents/Resources/o-iris-launcher.sh` (the bash launcher: offline install, passphrase dialog, then `exec oiris run`) with `/bin/bash` as a **child** process (`posix_spawn`, never `exec`). It passes the environment (e.g. `OIRIS_PASSPHRASE`, `OIRIS_PORT`) and its arguments through, forwards SIGTERM and SIGINT to the child, and exits with the child's exit status (128 + the signal number if the child was killed by a signal).
3. **Feeds the child the OS's cached Wi-Fi scan.** macOS reveals Wi-Fi BSSIDs only to the process holding the app's Location grant, which is this one: `system_profiler` run by the Python grandchild still had every BSSID withheld after the grant (macOS 26.5), and each `system_profiler SPAirPortDataType` run made macOS start a live scan, so that path was removed. Before the spawn it creates a pipe; the read end is inherited by the child and named in its environment as `OIRIS_WIFI_FEED_FD` (an inherited value of that variable is replaced, never passed on), the write end is `FD_CLOEXEC` and `O_NONBLOCK` and stays here. Every 15 s, on a background queue, while Location is `authorizedAlways`/`authorizedWhenInUse`, it reads `CWInterface.cachedScanResults()` (never `scanForNetworks`, never an association; macOS's Wi-Fi daemon log showed no scan requests from it, only power and supported-channel queries) and writes one JSON line: `{"t": unix_s, "status": "ok"|"location_not_authorized"|"no_interface"|"wifi_off"|"no_cached_results", "aps": [{"bssid", "rssi"}], "withheld": n}`, without SSIDs. A full pipe (the reader lags) drops the line; a closed reader (`EPIPE`, with SIGPIPE ignored here and reset to default for the child) stops the feed. Raw BSSIDs exist only in the pipe: the log gets feed state changes with counts (`wifi feed: ok, 31 networks (0 withheld)`), never an identifier. `oiris/adapters/macos.py` (`wifi_macos`) reads it; it is the only Wi-Fi source on macOS.

The main thread runs the main run loop (CoreLocation delivers its delegate calls on the run loop of the thread that created the manager); the child is reaped on a background queue and the exit happens on the main queue. No network, no UI of its own.

Why: macOS ties privacy permissions to the responsible app's code identity and only prompts when the app's main executable (with the usage strings in its Info.plist) asks. Requests from the Python child (bleak) or from a separate CLI helper without an Info.plist were dropped silently on macOS 26.5: O Iris appeared under neither Bluetooth nor Location. This Mach-O is ad-hoc signed together with the bundle by `scripts/make_macos_app.py`. It is built for arm64, so the bash launcher's Rosetta guard does not fire under it.

**Observed live** (Apple Silicon Mac, macOS 26.5, 2026-11-15): macOS showed the Bluetooth and Location prompts naming O Iris, the user allowed both, and the launcher logged `wifi feed: ok, 67–72 networks (0 withheld)`; `wifi_macos` stayed OK with a new sample about every 15 s. The reader side is also tested in-process with `os.pipe()` (`tests/test_macos_adapters.py`) and the launcher source is checked by `tests/test_macos_app.py`.

Build: `swiftc -O -target arm64-apple-macos14.0 main.swift -o o-iris` (`scripts/make_macos_app.py` does this when Xcode or the Command Line Tools are installed; `--no-swift` or `OIRIS_SKIP_SWIFT=1` skips it, and the bash script is then the executable as in earlier builds, with nothing asking for the permissions and no Wi-Fi source). So the app runs only on Apple Silicon with macOS 14 or later. Compiled with swiftc 6.3.2 on macOS 26.5. An earlier version without the permission requests was also exercised in a temporary fake bundle with a stand-in script (arguments, environment, exit status, SIGTERM/SIGINT forwarding, a child killed by a signal → 137). The bundle is ad-hoc signed, so every rebuild makes macOS ask for both permissions again (the identity is the code hash).
